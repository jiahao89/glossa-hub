## 一、审查综述与系统健康度

GlossaHub 在架构设计上具备优秀的工程化意识：双数据库抽象适配（SQLite 本地与 PostgreSQL/Supabase 生产）、乐观锁版本并发控制、双层术语库拦截过滤（全词直通与局部 Prompt 增强）、统一的审计日志链路与软删除回收站机制。

系统整体通过了 156 项自动化单元测试，构建打包正常（181ms 完成 Vite 生产构建）。但在深入代码审查后，仍发现了若干处**严重的数据丢失隐患、RBAC 角色权限越权漏洞、SSRF 安全风险以及元数据不一致问题**。

### 缺陷等级分布汇总

| 等级 | 数量 | 核心影响领域 |
|:---|:---:|:---|
| **致命 (Critical)** | 1 | 批量数据同步中的静默多语种翻译丢失 |
| **高危 (High)** | 4 | RBAC 权限越权绕过、SSRF 攻击面、PG 数据库全表初始化缺失 |
| **中危 (Medium)** | 5 | 词条编辑导致 TM/AI 标记丢失、语种变更元数据遗留、版本继承排序打乱、回收站跨项目数据穿透 |
| **低危/建议 (Low)** | 4 | SQLite 并发事务锁冲突、PG N+1 更新、React 渲染 Key 规范、多项目硬编码 |

## 二、致命与高危级缺陷 (Critical & High)

### 2.1 【致命·数据丢失】`sync` 同步接口更新分支漏查 `translations` 列，导致历史多语种被静默抹除
- **文件位置**：`server/routes/terms.cjs` 第 1354 行与第 1389-1391 行
- **失效机理**：
  ```javascript
  // 第 1354 行：SELECT 中只查了 kw, zh_cn, context, translations_meta，未包含 translations 列！
  const existing = await tx.queryOne('SELECT kw, zh_cn, context, translations_meta FROM terms WHERE id = $1', [rec.recordId]);
  
  // 第 1389 行：试图合并已有翻译，但 existing.translations 始终为 undefined
  let existingTrans = parseJsonField(existing && existing.translations); // 恒等于 {}
  const finalTranslationsObj = { ...existingTrans, ...translationsObj };
  const fieldsStr = JSON.stringify(finalTranslationsObj);
  ```
- **实际影响**：
  开发者在代码中明确写了注释 `// Merge with existing translations in database so previous language translations are preserved`，但因为 SQL SELECT 漏掉了 `translations` 列，导致 `existingTrans` 永远为空对象 `{}`。若调用者或部分前端逻辑仅传入单语种更新（例如只更新英文或只保存 AI 翻译的新语种），**该词条在数据库中已有的其他十几种语言翻译将被全部冲刷为空**！
- **修复方案**：
  在第 1354 行查询补全 `translations` 字段：
  ```sql
  SELECT kw, zh_cn, context, translations, translations_meta FROM terms WHERE id = $1
  ```

---

### 2.2 【高危·越权漏洞】只读角色 (`viewer`) 可通过 `sync`、`clean-empty`、`batch-*` 越权篡改全表
- **文件位置**：
  - `server/middleware/auth.cjs`（`requireVersionOwnership` / `requireAllTermsOwnership`）
  - `server/routes/terms.cjs`（`/tables/:tableId/sync`、`clean-empty`、`batch-update`、`batch-clear-translations`）
- **失效机理**：
  `requireVersionOwnership` 和 `requireAllTermsOwnership` 仅校验调用者是否为项目成员（`pm.user_id = $userId`），**从未校验成员角色是否为 `viewer`**：
  ```javascript
  // auth.cjs 第 82-90 行
  async function requireVersionOwnership(userId, versionId) {
    const user = await db.queryOne('SELECT role FROM users WHERE id = $1', [userId]);
    if (user && user.role === 'admin') return true;
    const ver = await db.queryOne(
      'SELECT v.project_id FROM versions v JOIN project_members pm ON v.project_id = pm.project_id WHERE v.id = $1 AND pm.user_id = $2',
      [versionId, userId]
    );
    return !!ver; // 只要是 viewer，ver 也存在，返回 true！
  }
  ```
  而在 `PUT /api/terms/:termId` 中，专门补充了只读检查：
  ```javascript
  if (termMembership && termMembership.role === 'viewer' && req.user.role !== 'admin') {
    return res.status(403).json({ error: 'FORBIDDEN', message: '只读审核人员无权修改词条。' });
  }
  ```
  但 `/api/tables/:tableId/sync`（批量增删改）、`/tables/:tableId/clean-empty`（删词条）、`/terms/batch-update`、`/terms/batch-clear-translations` 均只调用了 `requireVersionOwnership` 或 `requireAllTermsOwnership`，导致只读人员可通过 API 直接修改或清空词条。
- **修复方案**：
  在写操作路由统一增加角色检查：
  ```javascript
  const member = await db.queryOne(
    'SELECT pm.role FROM versions v JOIN project_members pm ON v.project_id = pm.project_id WHERE v.id = $1 AND pm.user_id = $2',
    [tableId, req.user.id]
  );
  if (member && member.role === 'viewer' && req.user.role !== 'admin') {
    return res.status(403).json({ error: 'FORBIDDEN', message: '只读审核人员无权修改词条。' });
  }
  ```

### 2.3 【高危·权限绕过】`/api/tables/:tableId/batch-generate-kw` 缺乏任何项目归属校验
- **文件位置**：`server/routes/terms.cjs` 第 1075-1090 行
- **失效机理**：
  该路由仅使用 `authenticateToken`，拿到 `tableId` 后只判断 `versions` 表记录是否存在，**完全没有调用 `requireVersionOwnership` 或 `requireProjectMember`**。任何拥有系统 Token 的外部登录用户，只要猜到或拿到其他租户的 `tableId`，即可批量篡改该版本内所有词条的 KW。
- **修复方案**：
  补齐项目归属与非只读角色校验。

---

### 2.4 【高危·SSRF 与凭证泄露】`/api/projects/:projectId/dify-test` 接受任意未过滤 `baseUrl`
- **文件位置**：`server/routes/translation.cjs` 第 722-765 行
- **失效机理**：
  用户通过请求体传入 `baseUrl`，服务端未做任何协议（仅限 https）、域名白名单或内网私有 IP 过滤（127.0.0.1, 10.x, 172.16.x, 192.168.x, 169.254.169.254），直接拼接 `${cleanBaseUrl}/workflows/run` 发起 `fetch`：
  ```javascript
  const targetKey = resolveBuiltinKey(targetUrl, apiKey, effective.apiKey);
  const response = await fetch(url, {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${targetKey}` }, // 携带真实 Key
    ...
  });
  ```
  这造成两项严重隐患：
  1. **SSRF（服务端请求伪造）**：可探测内网网络拓扑或云厂商元数据服务；
  2. **API 密钥外泄**：若用户传入攻击者控制的外网服务器 URL，后端会将内部 Dify API Key 通过 `Authorization` 头直接发送给攻击者服务器。
- **修复方案**：
  1. 严格校验 `baseUrl` 必须为有效合法的公网 HTTPS URL；
  2. 禁止解析至私有 IP / 本地回环地址；
  3. 若为自定义第三方 URL，严禁回退携带内置环境变量中的企业级 Dify 密钥。

### 2.5 【高危·数据库冷启动】PostgreSQL `ensureDbInit()` 缺少多数业务表 DDL
- **文件位置**：`server/config/db.cjs` 第 455-511 行
- **失效机理**：
  虽然根目录有完整的 `db_init_pg.sql`，但 `db.cjs` 中运行期的 `ensureDbInit()` 在连接 Postgres 时只执行了：
  - `projects`
  - `versions`
  - `terms`
  - `logs`
  未初始化 `users`、`project_members`、`languages`、`glossary_tables`、`glossary_terms`、`recycle_bin`、`term_snapshots`、`ai_usage_logs`。若在新数据库（如 Render PostgreSQL 或新建 Supabase）上启动服务，应用将在登录和语种查询时直接抛出 `relation "users" does not exist`。
- **修复方案**：
  将 `db_init_pg.sql` 的核心建表与索引逻辑同步至 `db.cjs` 的 Postgres 初始化代码块中，确保冷启动幂等性。

## 三、中危级缺陷与一致性问题 (Medium)

### 3.1 【中危·元数据丢失】`EditTermModal.jsx` 保存时重置 `translationsMeta`，导致 TM 绿勾消失
- **文件位置**：`src/components/translation/EditTermModal.jsx` 第 209-223 行
- **失效机理**：
  在单条编辑保存时，组件直接写死 `const translationsMeta = {};` 并随 PUT 请求提交至后端。后端直接覆盖数据库中的 `translations_meta`。
- **实际影响**：
  任何曾经由“翻译记忆库”（TM）匹配生成的词条，一旦在弹窗中进行哪怕微小的修改（如改负责人、纠正错别字），该词条所有语言的 `tm` 来源标记立即被擦除，界面上的绿色对勾（✅）永久丢失。
- **修复方案**：
  初始化时保留原有的 `record.translationsMeta`，提交时进行解构合并。

---

### 3.2 【中危·元数据不一致】语种改名与删除未同步处理 `translations_meta`
- **文件位置**：`server/routes/languages.cjs` 第 98-103 行、第 195-217 行
- **失效机理**：
  - 改名时：仅使用 PG JSONB 语法将 `translations` 中的旧键移至新键，但 `translations_meta` 中的键保持未动。
  - 删除时：仅从 `translations` 中 `delete trans[oldName]`，未从 `translations_meta` 移除。
- **实际影响**：
  语种改名后，前端读取该语种的元数据时命中不到新名称，标记失效；删除语种后，元数据中留下幽灵脏数据。

---

### 3.3 【中危·排序打乱】大表版本继承/克隆丢失 `sort_order`
- **文件位置**：`server/routes/versions.cjs` 第 111 行、第 134-149 行
- **失效机理**：
  `/inherit-chunk` 在 `SELECT` 基准版本词条时，未查询 `sort_order`；插入时也未指定 `sort_order`，全部落入默认值 `0`。
- **实际影响**：
  新继承生成的数据表所有词条的序号全变成 0，彻底失去原基准表的业务展示排序。

---

### 3.4 【中危·多租户数据泄露】回收站列表未按 `projectId` 隔离
- **文件位置**：`server/routes/recycleBin.cjs` 第 16-23 行
- **失效机理**：
  `GET /api/projects/:projectId/recycle-bin` 虽然路由带 `:projectId`，但底层 SQL 是：
  ```sql
  SELECT r.id, r.entity_type, r.entity_name, r.deleted_at, r.expires_at, u.name AS deleted_by_name
  FROM recycle_bin r
  LEFT JOIN users u ON r.deleted_by = u.id
  ORDER BY r.deleted_at DESC
  ```
  `recycle_bin` 表甚至没有 `project_id` 列，直接全库全量返回，不同项目的管理员能看到其他项目的废弃数据。

---

### 3.5 【中危·交互歧义】未勾选时点击“批量翻译”仅针对当前分页
- **文件位置**：`src/components/translation/TranslationTab.jsx` 第 226 行
- **失效机理**：
  `handleOpenBatchTranslate` 在未勾选行时使用 `let targetRecords = records;`。由于 `records` 仅为当前页的 50 条记录，若用户位于第 2 页，点击工具栏的“调用 Dify 批量翻译”只会翻译当前页，若当前页已翻完则提示“没有待翻译的词条”，令用户误以为全表已全部翻译完成。

## 四、低危级与架构演进建议 (Low & Refactoring)

### 4.1 SQLite 模式下并发事务缺乏 Mutex 串行化
- **位置**：`server/config/db.cjs` 第 676 行
- **说明**：SQLite 在 Node.js 单进程多异步请求时，若有两个写请求同时触发 `db.transaction()`，会导致第二个请求抛出 `SQLITE_ERROR: cannot start a transaction within a transaction`。本地单人开发不易触发，但多端联调或本地测试高并发时会报错，建议增加 `async-mutex` 或排队锁。

### 4.2 PG 删除语种时的 N+1 逐条更新性能问题
- **位置**：`server/routes/languages.cjs` 第 195-217 行
- **说明**：PG 分支在删除语种时，取出了所有词条在 Node 内存中循环发起单个 `UPDATE`。对于拥有上万词条的项目，将产生上万次网络往返。PG 具备原生 `-` 操作符，单条语句即可完成全量移除：
  ```sql
  UPDATE terms SET translations = translations - $1, translations_meta = translations_meta - $1
  WHERE version_id IN (...)
  ```

### 4.3 全局硬编码 `'proj-default'` 阻碍多项目演进
- **位置**：`TranslationTab.jsx`、`versions.cjs`、`dashboard.cjs` 等多处
- **说明**：多处接口默认将 `projectId` 写死为 `'proj-default'`。若后续开放多项目/多产品线功能，需要全面重构。建议由顶层上下文（Context）统一下发当前选中的 `projectId`。

### 4.4 React 列表渲染 Key 规范
- **位置**：`src/components/translation/BatchTranslateModal.jsx` 第 242 行
- **说明**：使用 `key={idx}` 渲染表格行，当行勾选或顺序变化时易导致 DOM 复用状态残余，应改为 `key={item.recordId || idx}`。
